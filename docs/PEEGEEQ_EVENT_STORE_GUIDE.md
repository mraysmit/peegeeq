## 1. Valid time and transaction time

An event store is an append-only table. A row is never updated. A correction is a new row that
points to the version it replaces. Each event carries two times.

| Time | Meaning | Who sets it |
|---|---|---|
| Valid time | When the fact is true in the business domain. | The caller, on every append. It can be in the past. The append paths reject a valid time more than one year in the future. |
| Transaction time | When the store recorded the event. | The store. It reads the JVM clock (`OffsetDateTime.now()`) just before the INSERT and writes that value. The column default `NOW()` is not used by the append paths. |

Transaction time is not commit time. The value is taken before the transaction commits. An
own-transaction append takes it before it acquires a connection, and a correction takes it before
it waits for the family's advisory lock, so the gap to the commit includes those waits. Two writers
can commit in the opposite order to their transaction times. Two application instances use two
clocks. Section 9 states what this means for pagination.

`BiTemporalEvent<T>` exposes the stored fields:

| Getter | Content |
|---|---|
| `getEventId()` | A random UUID string generated by the store. |
| `getEventType()` | The caller's event type, at most 255 characters. |
| `getPayload()` | The payload, stored as JSONB and read back as `T`. |
| `getValidTime()`, `getTransactionTime()` | The two times above. |
| `getVersion()`, `getPreviousVersionId()` | 1 and null for an original event. A correction has the next version and the ID of the version it replaces. |
| `getHeaders()` | String key-value metadata, stored in the `headers` JSONB column. |
| `getCorrelationId()`, `getCausationId()`, `getAggregateId()` | See section 6. |
| `isCorrection()`, `getCorrectionReason()` | Set on corrections only. |

The table also has a `BIGSERIAL id` column. It is not on `BiTemporalEvent`. Durable subscriptions
use it as their cursor (section 8).

## 2. Creating an event store

`BiTemporalEventStoreFactory` creates stores that use a `PeeGeeQManager`'s database configuration.
The table name is unqualified. The table must already exist in the manager's configured schema; the factory
does not create it. The [Database Guide](PEEGEEQ_DATABASE_GUIDE.md) describes how a table is
created.

```java
record OrderEvent(String orderId, String status, long amountCents) {}

BiTemporalEventStoreFactory factory = new BiTemporalEventStoreFactory(vertx, manager);
EventStore<OrderEvent> store = factory.createEventStore(OrderEvent.class, "order_events");
```

The two-argument factory constructor uses an `ObjectMapper` with `JavaTimeModule` and the
CloudEvents Jackson module. A third constructor argument supplies your own mapper.

Each store opens its own connection pool on first use and its own LISTEN connection on the first
subscription. `PeeGeeQManager.closeReactive()` does not close event stores. Close each store with
`close()` before you close the manager (read in code, not run). The
[Operations Guide](PEEGEEQ_OPERATIONS_GUIDE.md) shows a shutdown sequence.

A runnable example is `BiTemporalEventStoreExampleTest` in
`peegeeq-bitemporal/src/test/java/dev/mars/peegeeq/bitemporal/`.

## 3. Appending events

### The append builder

`EventStore.appendBuilder()` returns an `EventStoreAppendBuilder<T>`. `execute()` returns
`Future<BiTemporalEvent<T>>`. A missing event type, payload or valid time fails that Future with
`IllegalStateException`.

```java
Future<BiTemporalEvent<OrderEvent>> appended = store.appendBuilder()
    .eventType("order.created")
    .payload(new OrderEvent("order-123", "CREATED", 4999))
    .validTime(Instant.now())
    .correlationId("checkout-77")
    .aggregateId("order-123")
    .header("source", "web")
    .execute();

appended
    .onSuccess(event -> logger.info("Stored event {}", event.getEventId()))
    .onFailure(error -> logger.error("Append failed", error));
```

### Overloads

| Method | Transaction | Notes |
|---|---|---|
| `append(eventType, payload, validTime)` | Own | Deprecated in favour of the builder. |
| `append(eventType, payload, validTime, headers)` | Own | Deprecated. |
| `append(eventType, payload, validTime, headers, correlationId, causationId, aggregateId)` | Own | Not deprecated. The builder calls it. |
| `appendInTransaction(...)` with 4, 5, 6 or 7 arguments, the last one a `SqlConnection` | Caller's | Deprecated. |
| `appendInTransaction(eventType, payload, validTime, headers, correlationId, causationId, aggregateId, connection)` | Caller's | The builder calls it when `inTransaction(connection)` is set. |

An own-transaction append opens and commits a transaction on the store's pool. It does not join a
transaction the caller has open. To write the event in the same transaction as your own SQL, pass
the connection that holds your transaction:

```java
Future<BiTemporalEvent<OrderEvent>> recordInCallerTransaction(
        EventStore<OrderEvent> store, SqlConnection connection, OrderEvent event) {
    return store.appendBuilder()
        .eventType("order.created")
        .payload(event)
        .validTime(Instant.now())
        .aggregateId(event.orderId())
        .inTransaction(connection)
        .execute();
}
```

The event then commits or rolls back with the caller's transaction.

### Validation

The append paths fail the returned Future with `IllegalArgumentException` when:

- the payload is null, or the event type is null or blank;
- the valid time is null, or more than one year in the future;
- the event type, correlation ID, causation ID or aggregate ID is longer than 255 characters;
- a header key is null or blank, or a header value is null;
- the connection passed to `appendInTransaction` is null;
- the store is closed (`IllegalStateException`).

Through the builder, a missing event type, payload or valid time fails earlier with
`IllegalStateException`.

When the correlation ID is null, `append` and `appendInTransaction` store the new event ID as its
correlation ID.

### Batch append

`PgBiTemporalEventStore.appendBatch(List<BatchEventData<T>>)` is on the implementation class, not on
`EventStore`. It inserts the batch in one round trip (read in code, not run). All events in a batch
share one transaction time. `BatchEventData` has no causation ID field, the batch path does not
default the correlation ID, and it does not apply the validation above (D43).

## 4. Querying

`query(EventQuery)` returns `Future<List<BiTemporalEvent<T>>>`. `countEvents(EventQuery)` returns
the number of matching events; it ignores the limit, the offset and the keyset cursor.
`getById(eventId)` returns the event, or a Future that succeeds with `null` when no event has that
ID.

`EventQuery.builder()` accepts:

| Builder method | Effect | Default |
|---|---|---|
| `eventType`, `aggregateId`, `correlationId`, `causationId` | Exact match on the column. | No filter |
| `validTimeRange(TemporalRange)`, `transactionTimeRange(TemporalRange)` | `>=` start and `<=` end. Both ends are inclusive whatever the range's inclusive flags say (D43). | No filter |
| `headerFilters(Map)` | Each entry matches `headers->>key = value`. | None |
| `includeCorrections(boolean)` | `false` excludes rows with `is_correction = TRUE`. | `true` |
| `versionRange(min, max)` | `version >= min` and `version <= max`; either may be null. | None |
| `sortOrder(SortOrder)` | See below. | `TRANSACTION_TIME_ASC` |
| `limit(int)` | Must be positive. | 1000 |
| `offset(int)` | Must not be negative. | 0 |
| `after(Instant, String)` | Keyset cursor. See section 9. | None |

Sort orders, without a cursor:

| `SortOrder` | SQL ordering |
|---|---|
| `TRANSACTION_TIME_ASC` / `DESC` | `transaction_time`, then `valid_time` |
| `VALID_TIME_ASC` / `DESC` | `valid_time`, then `transaction_time` |
| `VERSION_ASC` / `DESC` | `version`, then `transaction_time` |

Static helpers build common queries: `EventQuery.all()`, `forEventType(type)`,
`forAggregate(id)`, `forAggregateAndType(id, type)`, `asOfValidTime(t)` (valid time `<=` t) and
`asOfTransactionTime(t)` (transaction time `<=` t). The two as-of helpers return every matching
version, not one row per event.

```java
EventQuery query = EventQuery.builder()
    .aggregateId("order-123")
    .eventType("order.created")
    .transactionTimeRange(TemporalRange.until(Instant.parse("2026-11-01T00:00:00Z")))
    .includeCorrections(false)
    .build();

store.query(query)
    .onSuccess(events -> logger.info("Found {} events", events.size()))
    .onFailure(error -> logger.error("Query failed", error));
```

`getUniqueAggregates(eventType, limit, offset)` lists aggregates with their event counts, first and
last event times and event types. `getStats()` returns totals for the store.

## 5. Corrections, versions and as-of reads

### Corrections

`appendCorrection` adds a new version of an existing event.

| Method | Stored correlation ID and aggregate ID |
|---|---|
| `appendCorrection(originalEventId, eventType, payload, validTime, correctionReason)` | None. Both columns are null. |
| `appendCorrection(originalEventId, eventType, payload, validTime, headers, correlationId, aggregateId, correctionReason)` | The values passed. |

The correction path, in one transaction (read in code, not run):

1. It resolves the root of the family from `originalEventId`. Any event ID in the family is
   accepted. An unknown ID fails the Future with `IllegalArgumentException`.
2. It takes a PostgreSQL advisory transaction lock on the root ID. Concurrent corrections of one
   family are serialised.
3. It inserts the correction with `version` = highest version + 1, `previous_version_id` = the ID of
   the current highest version, `is_correction = TRUE` and the reason.

A correction stores no causation ID. The correlation ID is not defaulted. A correction made with the
five-argument overload has no aggregate ID, so an `aggregateId` filter does not return it. Use the
eight-argument overload when you query by aggregate (D43).

The builder's `correction(originalEventId, reason)` calls the five-argument overload unless
`header(...)` or `headers(...)` with a non-null map was called; an empty map selects the
eight-argument overload. It does not apply `causationId(...)` or `inTransaction(...)` to a
correction (D41, D43). To correct with a correlation ID and an aggregate ID, call the eight-argument
`appendCorrection` directly:

```java
store.appendCorrection(originalEventId, "order.created",
        new OrderEvent("order-123", "CREATED", 4599),
        validTime, Map.of(), "checkout-77", "order-123",
        "Price corrected by the merchant")
    .onSuccess(correction -> logger.info("Version {} stored", correction.getVersion()))
    .onFailure(error -> logger.error("Correction failed", error));
```

On a closed store the call returns a failed Future (`IllegalStateException`). On an open store a
null `originalEventId`, event type, payload, valid time or reason throws `NullPointerException` from
the call; it does not fail the Future (D43).

### Versions and as-of reads

| Method | Result |
|---|---|
| `getAllVersions(eventId)` | Every version of the family that contains `eventId`, in version order. |
| `getAsOfTransactionTime(eventId, t)` | The highest version of that family whose transaction time is `<=` t, or `null` when none was recorded by then. |

The store has no query that returns one row per family as of a transaction time. To see what the
store held at time T, call `getAsOfTransactionTime` per event, or query with a transaction-time range
that ends at T and keep the highest version of each family.

## 6. Correlation and causation

| Identifier | Scope | Stored |
|---|---|---|
| `correlationId` | A business workflow. All events of one workflow share it. | Event column. Queue messages also carry a correlation ID. |
| `causationId` | The event that directly caused this event. Null for an event caused by an outside action. | Event column only. Queue messages have no causation ID. |
| `aggregateId` | The entity the event belongs to. | Event column. |
| Trace ID and span ID | One request across services, for log correlation. | Not a column. Present only as a `traceparent` header when the caller puts one in the headers. |

Causation belongs to the event store. A message sent through a queue does not carry or create a
causation ID.

### Recording a chain

Pass the parent's event ID as the child's causation ID:

```java
Instant now = Instant.now();

Future<BiTemporalEvent<OrderEvent>> chain = store.appendBuilder()
    .eventType("order.created")
    .payload(new OrderEvent("order-123", "CREATED", 4999))
    .validTime(now)
    .correlationId("checkout-77")
    .aggregateId("order-123")
    .execute()
    .compose(created -> store.appendBuilder()
        .eventType("order.paid")
        .payload(new OrderEvent("order-123", "PAID", 4999))
        .validTime(now)
        .correlationId("checkout-77")
        .causationId(created.getEventId())
        .aggregateId("order-123")
        .execute());

chain
    .onSuccess(paid -> logger.info("Chain stored, last event {}", paid.getEventId()))
    .onFailure(error -> logger.error("Chain append failed", error));
```

### Reading a chain

`EventQuery.builder().causationId(parentEventId)` returns the direct children of one event.
`EventQuery.builder().correlationId(id)` returns the whole workflow. The API has no call that walks a
chain of any depth. A recursive SQL query on the store's table does:

```sql
WITH RECURSIVE chain AS (
    SELECT event_id, event_type, causation_id, 0 AS depth
    FROM order_events
    WHERE event_id = $1
    UNION ALL
    SELECT e.event_id, e.event_type, e.causation_id, c.depth + 1
    FROM order_events e
    JOIN chain c ON e.causation_id = c.event_id
)
SELECT * FROM chain ORDER BY depth;
```

Flyway migration `V011` indexes `causation_id` on `bitemporal_event_log`. A table created from the
event store template has no `causation_id` index, because the template manifest does not list the
index file (read in code, not run; D42).

## 7. Live subscriptions

`subscribe(eventType, handler)` and `subscribe(eventType, aggregateId, handler)` register a
`MessageHandler<BiTemporalEvent<T>>`. The returned Future succeeds when the LISTEN is in place.
`unsubscribe()` stops the store's notification handler and removes every subscription on that store
instance.

```java
store.subscribe("order.*", message -> {
        BiTemporalEvent<OrderEvent> event = message.getPayload();
        logger.info("Event {} of type {}", event.getEventId(), event.getEventType());
        return Future.succeededFuture();
    })
    .onSuccess(v -> logger.info("Subscribed to order events"))
    .onFailure(error -> logger.error("Subscribe failed", error));
```

### Event-type rules

| `eventType` | Matches |
|---|---|
| `null` | Every event. |
| `order.created` | That event type only. |
| `order.*`, `*.created`, `*.order.*` | `*` stands for exactly one dot-separated segment. The segment count must be equal, so `order.*` does not match `order.line.added`. |

A non-null event type must be at most 50 characters. Each dot-separated segment must contain only
letters, digits and underscores, or be a single `*`. A blank or invalid value fails the Future with
`IllegalArgumentException`. These rules apply to live subscriptions only. Appends accept any event
type up to 255 characters, and an event type that breaks these rules cannot be subscribed to by
name.

### Delivery

An `AFTER INSERT` trigger on the store's table sends a PostgreSQL notification on two channels: one
for the table and one for the table and event type. The handler reads the full event with
`getById` and calls each matching subscription. The following are read in code, not run:

- Delivery is not durable. An event committed while no LISTEN connection is open is not delivered
  later.
- A handler failure is logged. The event is not redelivered.
- A handler can be called twice for one insert. When one store instance has both an exact-type
  subscription and a `null` or wildcard subscription, it listens on both channels. Each of the two
  notifications is dispatched to every matching subscription, and there is no deduplication (D43).
- When the LISTEN connection closes, the store reconnects up to five times, waiting 1, 2, 4, 8 and
  16 seconds. After the fifth failure it logs an error and stops; notifications stop until the
  application subscribes again.
- Before calling the handler, the store sets the MDC trace keys from the event's `traceparent`
  header, or creates a new trace ID when there is none, and sets `correlationId` and `messageId`
  (the event ID).
- A subscription with `eventType == null` and a non-null `aggregateId` is never called: the dispatch
  code has no branch for it (register D10). Subscribe with an event type, or filter by aggregate in the
  handler.

Use durable subscriptions (section 8) when an event must not be missed.

## 8. Durable subscriptions

A durable subscription stores its definition and cursor in the `bitemporal_subscriptions` table and
replays committed events in order. Its identity is `(tableName, subscriptionName, consumerGroup)`.
The handler is application code; it is not stored. After a restart the application must subscribe
again with a handler.

Create the service from a started manager. The manager closes the service in `closeReactive()`.

```java
BiTemporalSubscriptionService subscriptions = factory.createBiTemporalSubscriptionService();

SubscriptionOptions options = SubscriptionOptions.builder()
    .durableEnabled(true)
    .subscriptionName("order-projection")
    .startPosition(StartPosition.FROM_BEGINNING)
    .replayBatchSize(500)
    .build();

subscriptions.subscribe("order_events", "order-projection", "projections",
        "order.*", null, OrderEvent.class,
        message -> {
            logger.info("Replayed event {}", message.getPayload().getEventId());
            return Future.succeededFuture();
        },
        options)
    .compose(v -> subscriptions.deliveryCompletion("order_events", "order-projection", "projections"))
    .onSuccess(v -> logger.info("Durable delivery stopped"))
    .onFailure(error -> logger.error("Durable delivery failed", error));
```

`subscribe(...)` succeeds when the definition is stored and the first replay pass has run. When
that first pass fails, for example because the handler fails, `subscribe(...)` itself fails and the
delivery is removed; `deliveryCompletion(...)` then fails with `NoSuchElementException`. After a
successful start, `deliveryCompletion(...)` succeeds when delivery shuts down and fails on a terminal
delivery error (read in code, not run).

### Contract

| Item | Behaviour |
|---|---|
| Overload | Use the overload with `Class<T>`. The overload without it fails with `UnsupportedOperationException`. |
| Options | `durableEnabled(true)` and a `subscriptionName` equal to the name argument are required. |
| Start position | The default is `FROM_NOW`, which starts at the current highest `id`. `FROM_BEGINNING` starts at cursor 0. `FROM_MESSAGE_ID` sets the cursor to the given `id`; replay reads `id >` cursor, so the event with that `id` is not delivered. A start `id` above the current highest `id` is rejected. `FROM_TIMESTAMP` is rejected. |
| Filters | `eventType` and `aggregateId`, each checked only for a maximum of 255 characters. The wildcard matching of section 7 applies; its 50-character and segment-pattern checks do not. A re-registration with different filters fails. A re-registration with the same filters keeps the stored cursor and sets the subscription `ACTIVE`, so it resumes a `PAUSED` subscription. |
| Order | Events are replayed in `id` order, in pages of `replayBatchSize` (default 500, at most 10000). |
| Replay boundary | Each pass runs a short transaction with `SET LOCAL lock_timeout='5s'`, takes a `SHARE` lock on the table to wait for in-flight writers, and reads the highest `id`. Appends to the table wait behind that lock, for up to 5 seconds. Events at or below the boundary are replayed without gaps. The table's `id` sequence must be ascending, non-cycling and `CACHE 1`. A lock timeout or a sequence that fails the check stops delivery permanently (read in code, not run). |
| Acknowledgement | When the handler's Future succeeds, the cursor advances past that event in its own transaction. |
| Handler failure | Delivery stops. `deliveryCompletion` fails. The cursor stays on the failed event. The failed delivery stays registered in the service, so a new `subscribe(...)` for the same identity on the same service fails with "Handler already registered". Redelivery needs a new service instance or a process restart (D43). |
| Guarantee | At least once. A crash after the handler succeeds and before the cursor commits redelivers the event. Handlers must be idempotent. |
| Wake-up | Each live notification on the table, and a one-second timer. |
| Concurrency | One replayer per subscription holds a lease. An owner whose lease has expired cannot advance the cursor. |

Other operations on `BiTemporalSubscriptionService`: `pause`, `resume`, `cancel`, `resetCursor`,
`updateHeartbeat`, `getSubscription`, `listSubscriptions`, `catchUp` (one finite replay without live
delivery), `registerDefinition` (stores a definition without delivery) and `close`. `CANCELLED` and
`DEAD` are terminal. No background job marks a durable bi-temporal subscription `DEAD`.

`DurableBiTemporalSubscriptionIntegrationTest` and `DurableBiTemporalReplayIntegrationTest` in
`peegeeq-bitemporal/src/test/java/dev/mars/peegeeq/bitemporal/` exercise this API.

## 9. Keyset pagination

### Why

Offset pagination counts rows at query time. When events are appended between two page requests,
the row positions move, and a reader sees a row twice or misses one. Keyset pagination asks for the
events after the last event the reader saw. That anchor is a stored event, and new appends do not
move it. Navigation is sequential: a reader can go to the next page or back to a page whose anchor
it kept, but it cannot jump to page N.

### Java API

`EventQuery.Builder.after(Instant afterTransactionTime, String afterEventId)` sets the cursor. Both
arguments must be non-null. The sort order must be `TRANSACTION_TIME_ASC` or
`TRANSACTION_TIME_DESC`; any other sort order fails the query Future with
`IllegalArgumentException`.

```java
Future<List<BiTemporalEvent<OrderEvent>>> nextPage(EventStore<OrderEvent> store,
                                                   BiTemporalEvent<OrderEvent> lastSeen) {
    EventQuery query = EventQuery.builder()
        .aggregateId("order-123")
        .sortOrder(EventQuery.SortOrder.TRANSACTION_TIME_ASC)
        .limit(50)
        .after(lastSeen.getTransactionTime(), lastSeen.getEventId())
        .build();
    return store.query(query);
}
```

With a cursor the store adds `AND (transaction_time, event_id) > (anchor_time, anchor_id)` (or `<`
for descending) and orders by `transaction_time, event_id` in the same direction. The comparison and
the ordering use the same column pair, so equal transaction times are broken by `event_id`. The
tie-break is exact only while `event_id` is unique. `bitemporal_event_log` has a `UNIQUE(event_id)`
constraint (Flyway `V014`). A table created from the event store template has only a non-unique
index on `event_id`; there, uniqueness rests on the store generating `UUID.randomUUID()` (D43).

`countEvents` ignores the cursor and returns the full filtered total. A non-zero `offset` is applied
together with the cursor, so leave the offset at 0 on cursor queries.

### REST parameters

`GET /api/v1/eventstores/:setupId/:eventStoreName/events` accepts the cursor. The
[REST API Guide](PEEGEEQ_REST_API_GUIDE.md) owns the endpoint and its response.

| Parameter | Rule |
|---|---|
| `afterTransactionTime` | ISO-8601 instant, or epoch seconds as a decimal number. The API writes `transactionTime` in the decimal form (read in code, not run). Send the value back exactly as received: keep it as text, or convert it to ISO-8601 yourself. A client that parses the decimal as an IEEE double can lose digits; the anchor it sends back then differs from the stored value, and events tied on that transaction time are skipped or repeated (library behaviour, not run). |
| `afterEventId` | The anchor's `eventId`. Must be sent together with `afterTransactionTime`; one without the other returns 400. |
| `sortOrder` | `TRANSACTION_TIME_ASC` (the default) or `TRANSACTION_TIME_DESC` with a cursor. Another sort order with a cursor returns 400. |
| `limit` | Page size. Default 100. Values are clamped to 1 to 1000. |
| `offset` | Do not send it with a cursor. The store applies both the offset and the cursor. |

An `afterTransactionTime` that is neither format returns 400. The applied cursor is echoed in the
response's `filters` object; `filters.afterTransactionTime` is written in ISO-8601 form, not in the
decimal form of the events. `totalCount` is the filtered total without the cursor, computed again
on each request. `hasMore` is computed as `offset + eventCount < totalCount`. With a cursor the offset is 0, so
`hasMore` is `true` on every page unless one page holds the whole filtered total. Cursor clients
count the events they have read and compare that count with `totalCount`.

### What is guaranteed

Read in code, not run:

Both points assume a unique `event_id`, an offset of 0, and an anchor sent back with the exact
stored transaction time.

- **No overlap between cursor pages.** A page fetched with a cursor holds only events strictly after
  its anchor. The anchor's columns are never updated. Two pages of one cursor trail never return
  the same event.
- **No skip of visible events.** An event that was committed before a page was read, and that sorts
  after that page's anchor, is on that page or on a later page of the trail.

### What is not guaranteed, and when

- **Events that commit late are skipped.** Transaction time is taken from the JVM clock before the
  commit. An event can become visible after a reader has passed its position: a long caller-owned
  transaction, two concurrent writers, or two application instances with different clocks. A
  forward trail in ascending order does not return such an event (D43). A descending trail does not
  return events appended after its first page; they sort before it.
- **The first page orders differently.** A query without a cursor orders by
  `transaction_time, valid_time`, not by `transaction_time, event_id`. When events share a
  transaction time at the end of page 1, page 2 can repeat or miss events of that group (D43). A
  batch append gives all its events one transaction time. To give the first page the cursor
  ordering, start the trail with a cursor that precedes every event: in Java
  `after(Instant.EPOCH, "")` for ascending, or a far-future instant for descending; over REST
  `afterTransactionTime=0&afterEventId=0` for ascending.
- **Totals move.** `totalCount` reflects the store at each request.
- **A cursor belongs to one direction.** An ascending anchor is not valid for a descending trail.

A reader that must see every event in a stable order uses a durable subscription (section 8). It
reads in `id` order behind a writer barrier, not in transaction-time order.
